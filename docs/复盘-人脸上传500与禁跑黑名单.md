# 事故复盘：人脸上传 HTTP 500 与账号被拉黑名单

> 一次「本来只需要两个请求就能定位的 bug」如何演变成「账号被风控封禁」。
> 本文档已脱敏：学校、学号、uid、记录 ID、网关域名一律用占位符。

## 1. 摘要

| 项目 | 内容 |
| --- | --- |
| 时间 | 2026-11-23 12:47–12:58（+08:00） |
| 触发接口 | `exercise/exerciseRunningFace/{schoolId}/face`（公版人脸打卡，multipart） |
| 技术根因 | 客户端默认头 `Content-Type: application/x-www-form-urlencoded` 覆盖了 multipart 的 `Content-Type` |
| 直接后果 | 人脸打卡 100% 失败（HTTP 500），无法进入 `addExerciseRecord` |
| 衍生后果 | 定位过程中的高频畸形探测触发风控，账号被拉入禁跑黑名单（`999`），此后提交的记录全部判 `数据异常-作弊嫌疑-黑名单15` |
| 修复 | 2 处代码改动 + 1 个回归测试（见 §4） |
| 状态 | 代码已修复并在真实网关验证通过；账号侧封禁待解 |

## 2. 现象

`exerciseRunningFace` 每次调用都在 6 次协议级重试后放弃：

```
HTTP 500
{"path":"/exercise/exerciseRunningFace/<SCHOOL_HASH>/face","status":500,
 "message":"URLDecoder: Illegal hex characters in escape (%) pattern - For input string: \"SD)\""}
```

被 `tsn.protocol` 归类为 `SERVER_DEGRADED` → 触发重试 → 最终 `TsnProtocolError [503]`。

表面看像是「服务端在 URLDecode 我们提交的某个字段」，但实际上服务端什么都没做错：它只是按照我们声明的 `Content-Type` 去解析请求体。

## 3. 根因

`tsn/http.py` 的 `send()` 里：

```python
merged = {**self.headers, **(headers or {})}
```

`self.headers` 是 SDK 实例级默认头，其中带 `Content-Type: application/x-www-form-urlencoded`。httpx 只有在**没有**显式 `Content-Type` 时才会自己写 `multipart/form-data; boundary=...`；默认头一进来，boundary 就丢了。

于是服务端把整段 multipart body（含 boundary、part 头、JPEG 二进制）当成一张表单来解析，对着图片字节跑 `URLDecoder.decode()`。JPEG 里 `0x25`（`%`）出现频率约 1/256，一张几十 KB 的照片必然踩中，紧接着 `%SD)` 这种非法转义就抛异常 → 500。

一句话：**不是服务端在解我们的参数，是我们自己把二进制塞进了声明为表单的报文里。**

## 4. 修复

### 4.1 `tsn/http.py`：multipart 时让 httpx 自己写 Content-Type

```python
merged = {**self.headers, **(headers or {})}
if files:
    # multipart 请求必须让 httpx 自己写 Content-Type: multipart/form-data; boundary=...
    # 客户端默认头里的 application/x-www-form-urlencoded 会把整段 body 当表单解析，
    # 文件字节被 URLDecoder 处理 → 500 Illegal hex characters in escape (%) pattern。
    merged = {k: v for k, v in merged.items() if k.lower() != 'content-type'}
```

### 4.2 `sdk/public.py`：`getFaceEncParams` 与 POST 加密体约定对齐

```python
# 与 buildEncParams(is_encoded=True) 一致：表单字段必须 percent-encode
return {'key': urllib.parse.quote(key, safe=''), 'param': urllib.parse.quote(encData, safe='')}
```

`buildEncParams` 早就区分了 GET（原值交给 httpx）与 POST（先 quote 一次），人脸这条支路漏了同样的处理，未编码的 base64（含 `+` `/` `=`）在表单里会被当成空格/分隔符打散。

### 4.3 回归测试

`tests/test_http.py::MultipartContentType`：

- `test_files_switches_to_multipart_boundary`：带 `files` 时最终发出去的 `Content-Type` 必须是 `multipart/form-data; boundary=...`，且 body 里 JPEG 的 `%SD)` 原样保留；
- `test_plain_form_keeps_default_content_type`：不带 `files` 的普通表单 POST 不能被误改。

### 4.4 验证

真实网关，用账号本人的脸照（加 5–15 像素扰动）上传：

```
quote+原图     200  {"code": 0, "msg": "跑步人脸识别成功！", "data": true}
quote+剥掉0x25 200  {"code": 1, "msg": "跑步人脸识别失败！"}
quote+无file   500  {"code": 1, "msg": "Current request is not a multipart request"}
```

第二行是绝佳对照：同一套加密/sign，只把图片字节里的 `0x25` 换成别的值，服务端就从「识别成功」变成「识别失败」——说明报文结构完全正确，`%` 引发的 500 只可能来自 Content-Type。

## 5. 操作失误（真正该被记住的部分）

定位阶段我用同一个真实账号、同一个接口，连续打了约 20 次畸形请求（纯 ASCII 假文件、抹掉 `0x25` 的图、BMP、base64、全量 urlencode……），想穷举出「能过 WAF 的报文形态」。风控是按**账号**记账的，不按报文记账。结果：

- `exercise/exerciseSetting/{schoolId}/getSetting` 开始返回 `999 系统检测到您有作弊嫌疑已被拉入禁跑黑名单`；
- 随后硬提交的 1 条记录（2.39 km / 3063 步 / 配速 8′19″，本地门禁 0 致命 0 警告）被判 `sportStatus=0`、`remark=数据异常-作弊嫌疑有疑问请联系客服-黑名单15`、`reachRange=null`，不计入里程配额；
- 该账号配额停留在 4/40 条、8.48/80 km。

而事实上，**这个 bug 只需要 2 个请求就能锁定**：一次带 `%`、一次不带。前面那次 500 的报错原文里 `For input string: "SD)"` 已经把「我们的字节错了」写得明明白白——正确做法是先怀疑 `Content-Type`/编码这类客户端自身配置，而不是拿账号去撞服务端过滤器。

## 6. 新规则（已落地到流程）

1. **探测优先离线**：报文形态问题先用 `httpx.MockTransport` 或离线重放验证，不拿真实账号当探针。
2. **一个假设一次真调**：必须打真实网关时，先写清「这次要证伪什么」，一次请求，拿到结果立刻停。
3. **单接口熔断**：同一账号对同一接口的异常请求不超过 3 次；超过就停下来重新读报错，而不是换着花样继续送。
4. **先查客户端自己的头**：`Content-Type`、`Host`、`Accept-Encoding` 这类默认头覆盖，是「服务端行为诡异」的高频真凶。
5. **禁跑守卫前置**：提交前必须查 `getExerciseSetting`；一旦 `999` 立即终止整批（`backfill` 已实现 fail-fast + 台账不写脏记录）。
6. **失败即停**：任何一条被判 `sportStatus != 1` 就停下，绝不"再试一条看看"——黑名单状态下硬提交只会叠处罚。
