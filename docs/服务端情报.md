# 服务端情报（只读侦察记录）

> 本文记录对体适能（`com.bxkj.student`）服务端的一次**纯只读**侦察：
> 全部请求为 `GET` 静态资源或匿名接口，**未登录任何账号、未提交任何业务数据、未做任何写操作**。
> 目的：回答「能不能摸到服务端源码」这个问题，并把摸到的判定规则落成可执行结论。

---

## 0. 一句话结论

**服务端 Java 源码拿不到**（三道墙，见第 2 节）；
**但服务端的「判定规则说明书」拿到了** —— 它不是源码，效果却等价：
管理后台有一套 48 条的官方帮助中心，里面逐条写清了服务端会怎么判一次跑步（第 3 节）。
这批规则里有 **2 条当时是本地沙盘 `Judge` 没实现的**（点串里程 ≤ 2×步数、分段步幅 ≤ 2.5 m），**现已按原文补齐并加了单测**，逐条对账见第 5 节。

从中逐字还原出的**请求总入口**（与仓库 `sdk/public.py` 完全一致，说明协议层从来不是猜的）：

```js
// 签名：md5( AES-CBC( 按 key 排序的 "k=v&..." ) )，aesKey/aesIv 由 md5(token) 前后半段派生
function l(e, n, t, a) {
  var i = "" == e ? "appId=" + n + "&appSecret=" + t : e + "&appId=" + n + "&appSecret=" + t;
  return d(g(a, i.split("&").sort().join("&")));   // d = md5, g = AES-CBC
}
// 请求头
{ "Content-Type": d, sign: u, timestamp: i, Authorization: "Bearer " + uni.getStorageSync("uniIdToken"),
  school: l, uniqueCode: x() }   // x() = UA + 平台 + 语言 + 屏幕 + WebGL 指纹拼串
```

HTTP 状态分派（`function L`）：`200` 正常；`403` 鉴权失败；`404` 未发现服务；`423` 服务停用；

**关键负面结论**：整个 H5 包里 `exercise` 关键字命中 **0 次** —— 阳光跑（`addExerciseRecord`、人脸）
**不在 H5，只在原生 App 里**。所以要摸跑步链路，H5 只能佐证签名，拿不到业务实现。

## 4. 服务端自己的判定规则（48 条帮助中心，逐条摘录跑步相关）

这是**后端作者写给学生看的规则说明**，等价于源码注释。以下 20 条与跑步直接相关（原文照抄关键句）：

### 4.1 判定与处罚

- **「关于作弊记录处理方式」**：*「针对每条跑步记录，系统会在 **24 小时内进行二次监测分析**，
  当跑步记录出现异常（例如代步工具，网刷作弊）等情况时，跑步记录会自动被判定无效，
  同时体适能跑步账号会被加入黑名单，**期限为 7 天，7 天后自动解封**，黑名单期间内无法进行跑步锻炼。」*
  → 与仓库 `docs/逆向笔记.md` 里记的「15 天」不是同一档：**15 天是带 `-黑名单15` 后缀的加重处罚**，7 天是常规档。
- **「今日跑步已达上限、本周跑步已达上限」**：*「若今天跑步没提交，第二天提交的跑步记录，系统是按照**当天提交**的跑步记录算」*
  → 事后补交会算到提交日，不是跑步日。
- **「跑步记录申诉审核一直不通过？」**：老师批量审核，可带证件去体育部。
- **「为什么我的阳光跑总有效距离少于每条有效记录加起来的总和」**：*「当跑步实际距离大于**最大计入距离**时，
  首页计入的是计入距离，而点进去每条记录则是实际锻炼距离」*

### 4.2 三条**数据结构级**校验（沙盘需要对齐的）

- **「跑步记录提示轨迹距离校验异常？」**：*「当跑步的**轨迹距离大于步数的两倍**则会提示异常」*
  → 服务端确实拿点串累加距离和步数做了一次交叉校验：`累计里程(m) <= 2 × step`。
  2 km / 2200 步 → 比值 0.9 m/步，离 2.0 的线很远，安全。
- **「跑步详情中存在异常提示？」**：*「是因为在跑步中某一时间段**步幅超出正常范围，1 步里程大于 2.5 米**」*
  → 步幅上限 2.5 m/step（不是 1.2 m），且是**分段**判（原文「某一时间段」）。沙盘 `_worst_window_stride()` 按 60s 滑窗逐段取最大；实测本地生成器 60s 段最大 0.85–0.99 m/步，离 2.5 差一倍以上。本地门禁另一侧按人类区间收在 0.62–1.30 m，比服务端更严，是安全侧。
- **「人脸识别超出范围」**：*「体适能 App 在跑步过程中会**随机**进行人脸识别，当提示需要人脸识别的时候用户没有理会
  还在继续跑步，就会导致出现人脸识别超出范围」* → 说明三类人脸（首/中/末）是**App 侧主动触发**的，
  不是服务端按时间戳反查。沙盘 `Judge` 要求 `{1,2,3}` 齐全与这条一致。

### 4.3 环境与权限（为什么会「不计距离」）

- **「跑步不计距离，轨迹点漂移？」**：关省电模式 / 位置权限「始终允许」/ 允许后台运行 / 打开通知权限 / 设置里开健身运动。
- **「进行阳光跑提示无 GPS 信号？」**：到室外 / 开关定位 / 重进跑步 / 开关机。
- **「app 进行跑步时没有步数」**：健康运动权限；*「一定要**亮屏**跑步」*；步频靠手机传感器。
- **「跑步定位不准确不记录距离步数怎么办？」**：先关省电模式再开权限；*「app 提示权限未开启请开启权限**不用理会**，选择暂不开启，继续跑步」*
  → 这就是 `libSecShell.so` 那套权限/环境检测在客户端的表现，对应提交体里的 `environment.oppo/safe`。

### 4.4 上传与本地队列

- **「我存到本地的跑步记录不见了」**：记录存本地缓存，卸载即丢。
- **「完成跑步上传跑步记录时网络出现异常？」**：进「无效记录」找到本地那条点上传；清数据/卸载会清除。
- **「跑步记录上传失败、上传超时」**：*「由于大家跑步比较集中、网络拥堵、**流量限流限速**」*
  → 服务端有频率限制，对应本地 `tsn/http.py` 的 `RATE_LIMITED` 重试策略。

### 5.1 为什么那两条「上限」只能诊断，不能硬拒

先把 `tests/fixtures/records_qualified.json` 里 **5 条服务器判「合格」的真实记录**（`remark` 全是「合格」、
`status='1'`、`sportStatus='1'`）回放沙盘判定，逐条实测：

| 记录 id | 上报里程 | 步数 | 点串累加/步数 | 60s 窗口最差 m/步 | 服务端结论 |
| --- | --- | --- | --- | --- | --- |
| 9114388484495371621 | 2.010 km | 2109 | **3.805** | **7.468** | 合格 |
| 9150430287184064442 | 2.090 km | 1015 | **9.445** | **86.584** | 合格 |
| 9156722380507752559 | 4.010 km | 1059 | **10.832** | **396.339** | 合格 |
| 9174692058475414185 | 2.020 km | 2013 | **3.799** | **5.789** | 合格 |
| 9282319272228796097 | 2.050 km | 1004 | **7.414** | **60.243** | 合格 |

5 条**全部**违反「≤ 2×」和「≤ 2.5 m/步」两条线，而且是数量级地违反（最差 396 m/步）。
连「上报里程 ÷ 步数」这个口径也挡不住：4.010 km / 1059 步 = **3.787 m/步 > 2.5**，照样判「合格」。

结论：帮助中心那两句话要么只对特定跑型/版本生效，要么文案 ≠ 实现。**若当硬拒，会 100% 误杀真实合格记录。**
所以沙盘里它们降级为 `checks` 诊断字段（`chain_over_2x_steps` / `worst_window_over_limit`），
只记录、不拦截 —— 这条比「照抄文案」更接近真实服务端行为。

**取证**：`python run.py sandbox --count 3 --reject-demo` 会打印「真实『合格』记录回放」5 行，
每行都是 `[OK ]`；对应单测 `tests/test_sandbox.py::test_real_qualified_records_all_pass`。

### 5.2 `required_steps` 的递推分母是 `totalRange` 而不是 `rangeSetting`

原实现按 `rangeSetting`（2 km）做分母，于是 4.010 km 会要求 2005 步 —— 而上面那条真实合格记录
只有 1059 步。改成按 `totalRange`（14.2 km，阶段累计目标）做分母后，4.01 km 仍未超一圈，
要求恒为 `stepSetting`(1000)，与 5 条实测全对上。代码在 `tsn/submit.py:required_steps`。
